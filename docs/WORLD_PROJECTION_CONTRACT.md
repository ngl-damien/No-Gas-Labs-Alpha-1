# World Projection Contract

The game world is a projection, not an authority source.

## Boundary

Input is an append-only event sequence. A world consequence is admitted only when the event is simultaneously:

- `admission: ACCEPTED`
- `authority: AUTHORIZED`
- `execution: EXECUTED`
- `evidence: OBSERVED`
- `outcome: SUCCEEDED`
- backed by at least one receipt reference.

Claims and proposals may create visible quests, but cannot award XP, inventory, completion, or world mutations.

Failures, refutations, and rejected candidates remain in history.

## Source Archive failure objects

- A `source-archive-attempt-failed` event is appended by the shared Source Archive service only after it observes a retrieval/build failure. The server-only writer rejects any snapshot whose `revision` does not exactly equal retained `events.length` before cloning or appending, so partial or overfull histories cannot be advanced by a failure record. Clients cannot submit this event as an action. The retained event binds a unique attempt, request/action digests, repository, commit, path, failure code and retryability, and identifies `shared-source-archive-service`; raw request IDs and action fingerprints are not retained.
- Evidence Archive owns the complete paginated failure history. Moonshot Field may mirror a bounded newest-first subset as research blockers, using the same strict projection. This mirror does not change the failure's canonical Evidence Archive location. The incomplete Founder later-capture objective routes to Evidence Archive, where the exact failure card and its explicit Review source context lead are available; only that lead opens a prefilled Source Observatory form, and the form remains unretained until explicitly submitted.
- Opening a failure card, following its exact Chronicle event, or opening a prefilled Source Observatory lead is read-only. A lead is not an observation until explicitly submitted and server-validated. These actions create no event, XP, truth verdict, approval or authority.
- A failure-derived Source Observation carries originFailureEventId in normalized identity protocol v3. The identifier must resolve to exactly one earlier retained source-archive-attempt-failed event included in the declared sourceSnapshotRevision; a free-text mention of an event ID is not a link. The projector exposes the origin-link status and withholds linked progress when the event is missing, ambiguous, the wrong type, later in history, or excluded from the declared snapshot prefix.
- Founder and Witness failure-investigation objectives are actor-scoped projections of those exact linked observations. They do not count toward Questkeeper progression or award XP. The link establishes provenance to an operational failure only; source retrieval and independent verification remain NOT_PERFORMED, model assertions remain LEADS_ONLY, execution remains NOT_EXECUTED, and no truth verdict or authority is created.
- Later successful retrieval does not erase an earlier failed attempt. Partial, stale, invalid and unavailable projections must be distinguished; missing or unseen history is never interpreted as proof that no failure exists.
- `publicWorld` assigns each visible event its response-only global `historyPosition` before role-based filtering. A partial public projection may display that exact position only when every supplied event carries a safe, strictly increasing position within the declared revision; `visiblePosition` remains the ordinal inside the supplied view. Missing, mixed, accessor-backed, duplicate, non-monotonic, or out-of-range position metadata is not repaired or guessed. Preserving one visible event's position does not make the snapshot complete: capture matching remains UNKNOWN and no absence conclusion, XP, approval, or authority follows from the partial view.
- A later-capture link is eligible only for one unique, explicitly published Source Archive version whose parsed metadata says `SERVER_RECHECKED`, whose publication event is unique and exact, and whose recorded actor, repository, full commit SHA, and path match the failure. Both fetched/captured timestamps and the retained publication position must be later than the failure; retain the failure's append position in the projection instead of reconstructing causality from wall-clock timestamps.
- Later-capture absence is assertable only when retained creation/version records can be safely classified from plain records and own data fields, and every retained publish event resolves to exactly one retained creation/version. Exotic prototypes, accessor-backed `kind`, `intent`, or `html` fields, orphan publish events, and ambiguous creation links are never treated as absence; they make the capture projection UNKNOWN and withhold both positive and negative capture conclusions.

- Drafts, client-reported copies, different actors/targets, pre-failure fetches, ambiguous or duplicate publications, malformed source versions, and incomplete capture scans cannot establish a later capture. A complete history with no eligible match may say NOT OBSERVED; partial or ambiguous history must say UNKNOWN. Role-filtered public history now carries a response-only `historyCoverage` receipt (`ngl.public-world-history.v1`). It is emitted only when the server starts from a complete source history and records the source revision/event count, supplied event count, omitted event count, omitted event-type counts, and `viewerRole: "witness"`. The only omitted event types eligible for this projection are `draft`, `repair`, and `message-reported`; failure and publication events must remain visible. The receipt and per-event global `historyPosition` values are response metadata, not canonical events. `stripCompleteResponseHistoryPositions` strips them only from a complete 1..revision response; a role-filtered partial response remains non-canonical and cannot be imported as authoritative world state.

A positive Recovery Ledger link may be projected from that partial view only when every supplied event has a valid, strictly increasing retained global position; the coverage receipt's source revision, visible count, omitted count, role, and allowed omitted-type counts all reconcile exactly; the server-rechecked capture scan is complete; the exact repository/commit/path/version/publication pair is unique; and the aggregate comparison budget is not exhausted. The projector exposes a separate `recoveryLinkScanComplete` signal for this positive-link-only case. Overall `captureProjectionComplete` remains false for partial history. A uniquely observed positive link may make an existing, canonically retained pending item offer inspectable to its designated recipient, but it grants no XP, ownership, quest completion, authority, approval, or truth verdict.

Absence remains fail-closed: a partial history with no eligible match reports `UNKNOWN`, never `NOT OBSERVED`. If one publication matches multiple failure origins, or a failure has multiple eligible captures, the assignment scan becomes ambiguous, both completeness signals fail, all affected later-capture statuses remain `UNKNOWN`, and no Recovery Ledger link or quest progress is projected. A single publication cannot satisfy two failure-origin objectives.

The offline shared-snapshot envelope preserves the same receipt when it applies its additional privacy filter to witness-authored `message-reported` events: it increments that omitted-type count and recomputes visible/omitted counts before validation. The cache validator rejects receipts that omit any publication/failure event family or whose counts do not reconcile. Cached views remain read-only; consequential acceptance still requires a server-side action against the complete canonical history. The retained-version scan is bounded by one aggregate world-wide budget across creations. The failure-to-capture matching pass separately indexes captures by exact actor, repository, full commit SHA, and path, then applies one aggregate comparison budget across all failures. Either budget exhaustion yields a reason-coded UNKNOWN state and withholds every later-capture link rather than reporting NOT OBSERVED.
- The later link opens the exact retained artifact creation/version and exact publication event. It records a later byte retrieval and publication only: the failed response body is not retained, and the link does not establish byte equality with the failed response, source truth, authorship, claim accuracy, independent verification, execution, approval, or authority.
- The Founder-scoped two-event follow-up objective binds both the exact original failure event and exact later publication event. It awards no quest-completion XP and does not count toward Questkeeper progression; any ordinary publication reward remains governed by the existing explicit publish action.


## Field items and Armor Bearer handoffs

- A field item is a projection of one exact retained `field-item-forged` event and its validated source event. The Forge source index intersects the strict domain validator with the retained publication matcher; a type label or UI claim alone cannot mint an inventory item. The Recovery Ledger slot is Founder-scoped and requires one exact retryable `source-archive-attempt-failed` event plus one unique later `SERVER_RECHECKED` publication linked by actor, repository, full commit SHA, path, timestamps and retained append position.
- The Recovery Ledger keeps both exact lineage references: the original service-observed failure and the later publication/artifact version. Repository, commit, path, SHA-256, Git blob SHA and byte length describe the later retrieved bytes. They do not establish equality with the failed response, source truth, authorship, claim accuracy, independent verification, execution, approval or authority.
- The Field Kit's Recovery Lineage panel exposes `Open exact captured artifact vN` only when the retained creation ID and version pass bounded validation. It opens that exact edition against the accepted shared snapshot, including a cached offline snapshot; the artifact detail records `data-creation-id` and `data-creation-version`, and changing the version selector updates the selected-version marker. The artifact's own publication control opens the exact retained publication Chronicle event. These controls are read-only; unavailable or ambiguous editions remain unavailable, never fall back to the latest edition, and inspection creates no event, XP, ownership, approval or authority.
- Every validated Field Kit inventory card exposes a direct `Inspect Forge event` link when its exact `item.eventId` passes the safe event-ID shape, including before the item has any handoff history. It reuses the existing World Chronicle inspection callback and identifies the exact retained world event. The mobile regression checks the exact event card and unchanged world/XP; the link does not create an event, reward, ownership change, source verification, approval or authority. Run 348's exact-head Quest Board acceptance [45296264448](https://github.com/ngl-damien/No-Gas-Labs-Alpha-1/actions/runs/45296264448) passes this control in the 320px cache-only journey: the already-owned/equipped Witness Recovery Ledger opens its exact Forge event, exact captured artifact creation/version 1, and exact publication Chronicle event from the accepted snapshot. The run asserts zero additional API requests/POSTs, unchanged snapshot and pending-action store/revision, no XP, no horizontal overflow, and the same opaque-origin sandbox. The separate 390px pending-offer journey also opens the exact artifact version, failure event, and publication event. This is controlled-fixture navigation acceptance, not proof of external source truth or production persistence.
- Server-restart acceptance is exercised in `test/game-source-archive-restart.test.mjs`: a service-observed failure remains retained after the server process restarts; a new server-rechecked fixture capture and explicit publication link to that exact earlier failure; the Founder receives the Recovery Ledger source while a Witness does not; a Witness forge attempt is rejected without a revision or XP change; and Founder Forge/equip moves the Recovery Ledger objective from 2/4 to 3/4 to 4/4. The test uses a controlled upstream fixture and a temporary local filesystem store. It verifies server persistence/projection and actor scoping, not external source truth or production-host durability. The existing explicit publication reward is the only XP observed; Forge, equip and quest completion add none.
- Forge, equip and unequip are explicit actor-scoped inventory/loadout events. The creator is the initial owner; the exact source event and creator remain immutable across transfers. Equipment must reference the same retained Forge event and slot and the current owner. These actions grant no XP, combat statistic, mastery, evidence certification or institutional authority.
- A transfer offer is allowed only in the shared authoritative world. The server requires the designated recipient to have a live shared event stream; the reducer requires one exact item event, its current owner as sender, a different valid recipient, an unequipped item, a unique offer ID and no other active offer. A pending offer does not change ownership or recipient inventory.
- Only the exact designated recipient ID and role may accept or decline an active offer; only the current owner may cancel it. Acceptance appends one `field-item-transferred` event and changes current in-game ownership in the reducer. Decline or cancellation retains the offer outcome but leaves ownership unchanged. All offer/accept/decline/cancel and inspection actions are XP-neutral; neither session identity nor a completed game handoff establishes that two distinct humans participated.
- The Armor Bearer chain is reconstructed from four exact retained events in append order: (1) Forge the item; (2) the current bearer equips that exact item during their current ownership period; (3) the designated recipient accepts that exact offer; and (4) that recipient equips the exact item after transfer. A stale equip from an earlier ownership period cannot satisfy the bearer step. A transfer before the bearer equips remains in history but blocks the chain; the item must return and be equipped again before a later handoff can qualify. Timestamps do not reorder the chain.
- The initiating bearer receives the carry-forward objective only after the designated recipient accepts. Receiving an item is separate participation and does not count as carrying it onward. The recipient's equip is a separate fourth step. Quest/skill projections are deterministic views of these retained events; inspection and projection create no events, XP, mastery, approval, truth verdict or authority.

Replay is idempotent by `event_id`.

## Offline shared snapshot cache

- A shared snapshot cache is a read-only public projection, never an accepted server write, private draft store, source receipt, or authority source.
- Within one world ID, a cached snapshot with a higher accepted world revision is monotonic: a lower-revision snapshot cannot replace it, even when the incoming viewer actor or role differs. A different world ID begins a separate revision sequence.
- An accepted-position cache binds the exact viewer actor ID and role, world ID, and world revision. A position from another actor, world, or revision is rejected rather than applied.
- Position-cache schema v2 includes the world ID. Legacy v1 position entries without world identity are rejected.
- A cache hit is local display only. It does not prove a live session, current identity, canonical position, source truth, or permission to mutate. Shared cache-only mode remains read-only until the live server revalidates the session.
- The live revision guard begins only after the client accepts a shared server snapshot or an accepted read-only public cache. A private import is not a previously accepted shared snapshot, even if it preserves the shared world ID and has a higher local revision; the first shared join validates the incoming world identity without comparing against that private revision. Entering a private world or importing a private save resets this acceptance boundary. Once a shared snapshot is accepted, lower revisions for the same world remain rejected.

## Chronology and replay

- The retained event array position defines sequence. Replay must not sort events by wall-clock timestamp.
- Every event timestamp remains individually validated as strict normalized UTC metadata. A valid clock correction does not reorder an already appended event.
- `world.updatedAt` is a wall-clock high-water mark: it never moves backward when a later appended event carries an earlier timestamp.
- Only explicitly append-ordered action/event families may be appended below the current high-water mark: Source Observatory observation/challenge/response actions; Combat Yard encounter-start/move actions; Polymath Academy study/review actions; and R&D/Guild collaboration records (Moonshot proposals, experiment reports, cross-actor challenges, original-author responses, shared-server Source Archive predicate evaluations and failure records, and bounded collaborator responses). Each referenced publication, proposal, report, challenge, or collaborator packet source must be unique and earlier in the retained event array. An experiment response must follow its exact challenge and remain authored by the original report actor; a collaborator response remains advisory-only and source-packet-bound. Source Archive predicates remain server-evaluated against exact retained bytes, while failures remain server-observed history. Strict per-event UTC timestamps remain metadata and need not increase across these append-ordered sequences; world.updatedAt remains the maximum timestamp. All other world actions/events remain chronology-gated and reject timestamp regression.
- This exception changes neither actor authorization nor the admission/evidence requirements above. Academy study and retrieval review remain self-reported practice; experiment reports remain self-reported attempts; collaborator output remains a bounded lead; Source Archive predicates establish only a literal property of retained bytes; and operational failure records establish only that the shared service recorded a failure. These events grant no XP or mastery and cannot establish substantive correctness, truth, authority, approval, or a successful outcome.

Verified revocations are replayed in event order. They block later executions using the revoked grant, and the quest projector applies the same boundary as the world reducer. A revocation does not silently erase earlier verified outcomes; the original event and its consequence remain auditable in history.

- Shared R&D projection: Quest Board objective progress and Character Sheet research skills consume the same validated `projectResearchRecords` projection. Retained event positions order proposal → report → cross-actor challenge → original-author response and bind supplied evidence to one exact earlier published version. Strict UTC timestamps remain required metadata but do not order this chain. A challenge may omit optional evidence; if it supplies evidence, it must link. Unlinked, ambiguous, malformed, or reordered records remain in history but do not advance objective/skill projections. These activity counts do not establish truth, mastery, XP, approval, or authority.
- Moonshot Field displays an experiment challenge response as `AUTHOR RESPONSE · NOT ADJUDICATION` only when the response's own `projectResearchRecords` result is safe, has a unique event ID, and carries `targetChallengeStatus: linked` with the exact target challenge/report/Moonshot and original report actor. Raw presence under a challenge, or matching report labels alone, is not sufficient. Blank or untrimmed response IDs are rejected by both `validateWorld` and the independent stored-history validator so canonical history validation agrees with the projector. Invalid or incomplete responses remain retained as warnings, not author replies. This is an event-link/actor-attribution check only; it does not prove distinct human participants, truth, adjudication, evidence, XP, approval, or authority.

- **RAE (executable source inspected):** bounded no-follow byte reads, deterministic observation IDs, structured predicates, self-integrity receipts, and signed operation-scoped capability grants. Its verifier deliberately leaves model claims `PROPOSED` even when a receipt validates; a receipt establishes artifact identity/self-integrity, not claim semantics.

The public `adrianjonmiller/runeux` repository describes itself as a JavaScript function-trampoline utility, not an MMORPG UI or world runtime; it is not implementation evidence.
- **Guild/Command Center (interface patterns only):** useful collaboration and operational-surface concepts. The recovered Guild demo simulates task outcomes/metrics, including random values; Command Center Node-Gate hook state is not signed authority or canonical progression.
- **TownSquare (not an executable donor in the recovered copy):** the active `No_Gas_Labs-Omnichain_TownSquare` repository contains a README describing a one-file/two-line archive; no executable MMORPG runtime was recovered there.
- **AGP/VoxScript (publication and drafting patterns only):** AGP's demo backend uses in-memory state and random metrics; VoxScript uses heuristic satire scoring, a hardcoded compliance score, and a placeholder fact-checking integration. These outputs are not evidence, approval, or verification.
- **Decision Chamber (Alpha-1 module, not a separate donor repository):** the current authority module verifies exact scoped ECDSA P-256 Founder decisions with fingerprint, nonce, and expiry checks. The repository's Founder trust anchor remains `NOT_ENROLLED`; tests use `TEST_ONLY` keys.

The reducer does not claim these donor systems are already wired into Alpha 1. It creates the boundary through which independently inspectable mechanisms may be adapted without allowing the game UI, a model assertion, a demo metric, or an imported report to manufacture canonical state.

## TownSquare review-map actor-visible history coverage (Run 358)

- `projectTownSquareReviewObjects` is a read-only projection over the exact retained `message-posted` → `message-reported` → `message-report-reviewed` chain. A marker is not a canonical event, moderation action, adjudication, evidence certification, approval, truth verdict or XP grant.
- Founder snapshots require a complete dense event history. Missing coverage on a revision-mismatched snapshot, malformed/accessor-backed coverage, a post-receipt truncation, unsupported omitted event family, or inconsistent omission counts makes the actor-visible history incomplete.

- This is a structural response-consistency check, not a cryptographic signature, independent source observation, proof of truth, proof of exhaustive server history, or grant of authority. The canonical server/event validator remains the authority boundary; model/NPC/UI assertions cannot manufacture evidence or progress.
